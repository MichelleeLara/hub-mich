1 · Toggle de tema claro/oscuro

dark-mode-toggleThemetoggle.jsx:21Layout.astro:64product.css

El tema se guardaba en localStorage y se aplicaba con la clase .dark y un style.colorScheme en línea, sin <meta name="color-scheme">.

Antes 
// Themetoggle.jsx
const next = isDark ? 'light' : 'dark';
root.classList.toggle('dark', next === 'dark');
root.style.colorScheme = next;
localStorage.setItem('theme', next);
  • Un clic fijaba el tema para siempre, aunque coincidiera con el sistema.
  • Si el sistema cambiaba de claro a oscuro (horario automático), la página no se enteraba.
  • Otra pestaña abierta no se actualizaba.
  • color-scheme dependía de JS en línea.
Después 
<meta name="color-scheme" content="light dark">
/* product.css */
:root { color-scheme: light dark; }
:root:has(> head > meta[content="dark"])  { color-scheme: dark; }
:root:has(> head > meta[content="light"]) { color-scheme: light; }

// Themetoggle.jsx
const stored = (next === 'dark') === systemDark()
  ? null : next;           // igual al sistema = borrar
applyScheme(stored);       // meta + clase .dark
  • Dos estados: «sigue al sistema» o «el contrario del sistema».
  • Volver al tema del sistema borra el override.
  • Sin override, sigue al sistema en vivo (matchMedia).
  • Se sincroniza entre pestañas (evento storage).
  • Tailwind sigue usando .dark; no se tocó ningún estilo.
Regla de la guía: If the target matches the current system preference, the user is undoing their adjustment: remove the stored value.

2 · Diálogo de vista previa de proyectos

dialogProjectsGallery.astro:214

El clic fuera del <dialog> se detectaba a mano con coordenadas, y el scroll de fondo se bloqueaba con html { overflow: hidden }.

Antes 
dialog.addEventListener('click', e => {
  if (e.target !== dialog) return;
  const box = dialog.getBoundingClientRect();
  if (fuera(e, box)) close();
});
html.project-preview-open { overflow: hidden; }
  • Un arrastre de selección que terminaba fuera cerraba el diálogo.
  • overflow: hidden en html quita la barra de scroll de la raíz.
Después 
<dialog class="project-preview" closedby="any">
/* el cancel ya existente cierra con la animación */
.project-preview::backdrop {
  overflow: hidden; overscroll-behavior: contain;
}
// Solo si falta closedBy (Safari):
if (!('closedBy' in HTMLDialogElement.prototype)) {
  pointerdown + pointerup fuera → close()
}
  • Clic fuera nativo: dispara cancel y reutiliza el cierre animado.
  • Fallback para Safari que exige presionar y soltar fuera.
  • El scroll de fondo se contiene sin tocar html.
Regla de la guía: Require the press and the release outside, so a text-selection drag that ends on the backdrop does not dismiss.

Coincidimos en el enfoque general; la diferencia es el riesgo en Safari, que la guía acepta y Codex considera una regresión.

Riesgos y decisiones pendientes

  • Safari y el scroll detrás del diálogo. Safari no soporta overscroll-behavior en el fondo; la guía acepta que ahí la página pueda moverse detrás del modal antes que volver a overflow: hidden. Si prefieres el bloqueo total, se restaura esa línea (la barra de scroll ya tiene scrollbar-gutter: stable, así que no hay salto de layout).
  • Sin JavaScript. El HTML trae class="dark" fijo, así que sin JS el sitio queda oscuro aunque el sistema esté en claro. La guía pide no depender de clases de JS; arreglarlo exige migrar colores a light-dark(), fuera de este barrido.
  • Bloqueo de render. #main-content envuelve toda la página, así que el primer pintado espera a que se lea todo el HTML (80–225 KB, milisegundos). La guía prefiere apuntar a un elemento visible al cargar; si Lighthouse muestra un FCP más lento, se cambia por un marcador en el hero.
  • Toggle visible siempre. La guía recomienda no tener un toggle persistente en la barra. Se dejó porque es decisión de diseño.
